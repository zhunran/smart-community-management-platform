# 物业管理系统 - 业务全景

> 本文档回答四个问题：**系统做了哪些业务、解决了什么实际问题、每个业务怎么实现、为什么这么设计**。面向业务理解，技术细节见 `关键实现逻辑.md`。

---

## 一、系统定位与核心价值

这是一套面向 **物业管理方 + 业主/住户** 的一体化物业管理系统，覆盖物业运营的完整闭环：

```
资源管理（房屋/车位/业主）
   → 计费（账单生成）
   → 收缴（线上支付/线下缴费）
   → 运营（逾期催缴/通知公告/车位营运）
   → 治理（对账/审计/统计）
   → 服务（AI 客服答疑）
```

核心价值：**把物业公司"手工做账、线下收费、被动追缴、数据靠记"的日常，变成自动化、在线化、可追溯、可监督的平台。**

系统分两端：

| 端                          | 端口 | 用户       | 定位                                                 |
| --------------------------- | ---- | ---------- | ---------------------------------------------------- |
| 管理端 `property-admin-api` | 8081 | 物业管理员 | 房产业主管理、费用设置、账单操作、支付记录、审计统计 |
| 业主端 `property-owner-api` | 8084 | 业主/住户  | 自助查账单、在线缴费、车位办理、AI 咨询              |

## 三、分业务域详解

### 3.1 认证与账号 —— 两端隔离 + 双 Token

**做什么**：管理员（用户名+密码）与业主（手机号+密码+图形验证码）双端登录，JWT 双 Token 鉴权。

**解决什么问题**：

- 管理端与业主端权限完全不同，混在一起容易越权；
- Token 长期有效易泄露，短效则用户频繁登录。

**怎么实现**：

- `JwtUtil` 签发 **Access Token（短效，含完整用户信息，type=access）** 与 **Refresh Token（长效，仅 userId，type=refresh）**；
- Access 走 `httpOnly Cookie path=/` 随请求携带，Refresh 走 `path=/api/{admin|owner}/auth/refresh` 仅刷新接口携带；
- 拦截器 [AuthInterceptor](file:///d:/.workspace/javaproject/property-management-system/property-management/property-framework/src/main/java/com/property/framework/web/interceptor/AuthInterceptor.java) 默认拦截 `/api/{admin|owner}/**`，靠 `@SkipAuth` 注解精确放行登录类接口。

**为什么这么选**：

- **双 Token**：Access 短效（泄露面小）+ Refresh 长效（体验好），并通过 Redis 存储 Refresh 使服务端可随时吊销，是"安全 vs 体验"的平衡；
- **httpOnly Cookie 传输**：防 XSS 脚本读取 Token（内存里拿不到），相比 localStorage 更安全；业务请求只在 Access 上校验，Refresh 因 path 受限不会随业务请求外泄。

### 3.2 房产资源管理 —— 共享数据层 + 三级层级

**做什么**：维护楼栋、单元、房屋三层基础档案数据，为其他业务模块提供统一的数据查询入口。

**解决什么问题**：

- 房产数据（楼栋/单元/房屋）被账单、业主、车位等多个业务模块依赖，分散在各模块中会导致数据不一致和循环依赖；
- 房屋面积、房号等基础信息是计费、业主关联、车位绑定的共同前提。

**怎么实现**：

- [BuildingEntity](file:///d:/.workspace/javaproject/property-management-system/property-management/property-module-housing/src/main/java/com/property/module/housing/entity/BuildingEntity.java) → [UnitEntity](file:///d:/.workspace/javaproject/property-management-system/property-management/property-module-housing/src/main/java/com/property/module/housing/entity/UnitEntity.java) → [RoomEntity](file:///d:/.workspace/javaproject/property-management-system/property-management/property-module-housing/src/main/java/com/property/module/housing/entity/RoomEntity.java) 三级层级结构，通过 `buildingId`/`unitId` 外键关联；
- 模块不对外暴露 REST API，写操作通过 admin-api 的 `AdminBuildingController`/`AdminUnitController`/`AdminRoomController` 完成；
- 读操作通过 [RoomDataService](file:///d:/.workspace/javaproject/property-management-system/property-management/property-module-housing/src/main/java/com/property/module/housing/service/RoomDataService.java) 接口对外暴露 9 个查询方法，供 bill/owner/parking 等模块通过 Spring 依赖注入调用。

**为什么这么选**：

- **无 Controller 设计**：房产数据的增删改属于管理端操作，放在 admin-api 中统一管理；模块自身作为纯数据层，避免职责重叠；
- **共享数据层**：将物理房产数据独立为一个模块，避免被任何单一业务模块"拥有"，保证数据访问的一致性和模块间解耦。

### 3.3 业主管理 —— 多对多关系 + 字段级权限

**做什么**：维护业主档案，管理业主与房屋的关联关系。

**解决什么问题**：

- 现实中"一套房多个共有人、一个业主多套房"，一对多模型表达不了；
- 业主自改信息时不能碰身份证号、状态等敏感字段（越权）。

**怎么实现**：

- `t_owner_room` 关联表：`ownerId + roomId + relationType(业主/家属/租客) + isPrimary(是否主业主)`；
- 手机号/身份证唯一性校验**含逻辑删除记录**，避免与已删记录冲突；
- 新增业主默认密码 = 手机号后 6 位，BCrypt 加密存储；
- 管理端 `OwnerUpdateRequest` 可改所有字段，业主端 `OwnerProfileUpdateRequest` 通过 [MapStruct `@Mapping(ignore=true)`](file:///d:/.workspace/javaproject/property-management-system/property-management/property-module-owner/src/main/java/com/property/module/owner/converter/OwnerConverter.java) 排除敏感字段。

**为什么这么选**：

- **多对多 + 关系类型 + 主业主标记**：既表达真实生活关系，又能唯一定位"房屋负责人"（主业主唯一，绑定新主业主时重置旧主业主）；
- **MapStruct 双 DTO**：在转换层就拦掉敏感字段，比在 Controller 里逐个判空更集中、不易漏，符合"字段级授权"。

### 3.4 账单与收费 —— 四种计费 + 幂等生成 + 状态机

**做什么**：按月生成物业费账单，支持整单/分项缴费，逾期自动标记与计罚息。

**解决什么问题**：

- 物业计费模式多样（按面积/按户/按用量/固定），人工算账易错；
- 账单若重复生成会导致业主多缴费、账目混乱；
- 逾期催缴依赖人工记忆，容易漏。

**怎么实现**：

- 四种计费方式（[BillServiceImpl](file:///d:/.workspace/javaproject/property-management-system/property-management/property-module-bill/src/main/java/com/property/module/bill/service/impl/BillServiceImpl.java)）：`按面积(面积×单价×月数) / 按户(单价×月数) / 按用量(预估用量×单价) / 固定金额`；
- 生成幂等：同房屋同账期存在非终态账单则跳过；账单号 `BILL+yyyyMMdd+4位流水`；
- 状态机：`UNPAID → PARTIAL → PAID`，`OVERDUE` 可继续缴费，终态 `PAID/VOIDED/DISCOUNTED` 不可再缴；
- 整单缴费用 `SELECT ... FOR UPDATE` 行级锁防并发超收，分项缴费用 `SET paid_amount = paid_amount + ?` 原子累加；
- 逾期：扫描 `due_date < today`，标记 OVERDUE，罚息 = 未缴金额 × 日利率 × 逾期天数（上限 100%）。

**为什么这么选**：

- **calcType 抽象**：把差异化的计费规则统一到"计价公式"，新增费用类型只配参数不改代码，避免每种费用一套逻辑；
- **幂等 + 定时生成**：账单必须"每月自动、可重跑"——任务重跑不会重复，是定时任务可靠性的前提；
- **行级锁兜底收钱场景**：金额场景冲突后果严重，宁可串行，也要绝对避免"超收/少收"。

### 3.5 支付 —— 支付宝接入 + 三重防重 + 主动对账

**做什么**：对接支付宝电脑网站支付，处理异步回调，主动对账补偿。

**解决什么问题**：

- 居民线下缴费跑腿、物业对账繁琐 → 在线支付；
- 支付回调可能**重复推送**（网络重试）或**丢失**（超时/断网），"钱到账但账单没更新"是致命问题。

**怎么实现**：

- 后端构建支付表单 HTML 返回前端，前端提交跳转支付宝收银台；
- 下单防重：同账单已有待支付订单则**复用**，不重复建单；
- 回调三重防重（[PaymentCallbackService](file:///d:/.workspace/javaproject/property-management-system/property-management/property-module-payment/src/main/java/com/property/module/payment/service/PaymentCallbackService.java)）：Redis 分布式锁 → 行级锁 FOR UPDATE → 乐观锁 `WHERE status=?` → 幂等检查（终态跳过）；
- 主动对账（[PaymentReconciliationService](file:///d:/.workspace/javaproject/property-management-system/property-management/property-module-payment/src/main/java/com/property/module/payment/service/PaymentReconciliationService.java)）：扫描 30 分钟前待确认订单，逐条安全查询支付宝交易状态并纠正。

**为什么这么选**：

- **多重防重**：支付是全系统"最不能错"的场景。单靠任何一层都有盲区——分布式锁防并发、行级锁串行化、乐观锁最终兜底、幂等检查防重复处理，层层递进确保"至少一次投递、恰好一次生效"；
- **主动对账补偿**：不依赖被动回调的可靠性，用定时查单兜底，保证"最终一致"——即使回调丢了，对账任务也会把账单补对。

### 3.6 车位管理 —— 乐观锁 + 双轨对账预警

**做什么**：车位出售/出租登记、绑定/变更/退租，车位账实一致性对账。

**解决什么问题**：

- 车位并发被重复绑定/退租导致状态冲突；
- 系统记录与实际车位状态不一致（账实不符）难以发现。

**怎么实现**：

- [ParkingSpaceEntity](file:///d:/.workspace/javaproject/property-management-system/property-management/property-module-parking/src/main/java/com/property/module/parking/service/impl/ParkingSpaceServiceImpl.java) 用 `@Version` 乐观锁，绑/变/退租校验 `updateById` 影响行数，失败即"已被他人修改"；
- 所有变更写 `t_parking_change_log` 变更日志（新旧值、操作人）；
- 双轨对账：执行 5 类 SQL 比对（租赁到期/车位闲置/支付待处理/占用异常/租赁即将到期），每类前先去重避免重复预警。

**为什么这么选**：

- **乐观锁而非悲观锁**：车位操作并发冲突概率低、争议后果相对轻，乐观锁开销小、不长期占锁，性能更优——与支付/缴费场景（冲突后果严重、用悲观锁）形成对比，体现"按冲突严重程度选锁"；
- **双轨对账**：从"被动等投诉"转为"主动发现异常"，5 类预警覆盖常见账实不符场景。

### 3.7 通知公告 —— 生命周期 + 邮件催缴

**做什么**：物业公告发布管理、逾期账单邮件催缴。

**解决什么问题**：公告传达不及时、逾期催缴靠人工电话耗时低效。

**怎么实现**：

- 公告生命周期：草稿 → 发布 → 定时上下线；
- 逾期通知定时任务按 ownerId 分组，查业主邮箱，用 Thymeleaf 模板发送催缴邮件。

**为什么这么选**：

- 模板化邮件让催缴内容统一、可批量、可追踪，替代人工逐一电话/上门。

### 3.8 统计与审计 —— 经营报表 + 操作留痕

**做什么**：缴费趋势、仪表盘汇总、操作审计日志。

**解决什么问题**：物业经营数据不透明、管理人员操作无痕难追责。

**怎么实现**：

- 缴费趋势：按日期聚合缴费人数与金额（ECharts 双 Y 轴）；
- 审计日志：`@OperationLog` 切面异步落库（时间、账号、模块、动作、方法、URL、IP、状态、耗时、结果）。

**为什么这么选**：

- **异步落库（单线程守护线程池）**：日志是旁路，不能拖慢主业务响应；单线程保证写入顺序与无竞态；
- 审计保留"操作人 + 参数 + 结果 + 耗时"，满足事后追责与安全审计。

### 3.9 AI 客服 —— Spring AI 多轮对话 + 工具函数

**做什么**：业主端 AI 智能客服，可查账单、查房屋、查公告、看小区简报。

**解决什么问题**：居民高频重复咨询（我的账单、欠费多少、最新公告），消耗物业大量人力。

**怎么实现**：

- `ChatClient` 流式对话 + `MessageChatMemoryAdvisor` 会话记忆（多轮上下文）；
- `@Tool` 工具函数：查账单、查房屋、查最新公告、小区简报；
- 业主端用原生 `fetch` + `ReadableStream` 解析 SSE 实现打字机效果。

**为什么这么选**：

- **SSE 而非 WebSocket**：AI 回复是单向流式，SSE 足够且更简单、易穿透代理、自动携带 httpOnly Cookie 鉴权；
- **工具函数（Function Calling）**：让 AI 能查真实业务数据而非"编造"，把对话能力与业务查询打通，回答可信。##之后还会加入rag检索，添加社区规章与社区信息的检索功能

### 3.10 定时任务 —— XXL-Job 自动化运营

**做什么**：账单生成、逾期扫描、逾期通知、支付同步四个定时任务。

**解决什么问题**：账单/催缴/对账这类"周期性、量大、易漏"的工作自动化。

**怎么实现**（[property-task](file:///d:/.workspace/javaproject/property-management-system/property-management/property-task/src/main/java/com/property/task/job/BillGenerateJob.java)）：

| 任务     | 频率       | 逻辑                                   |
| -------- | ---------- | -------------------------------------- |
| 账单生成 | 每月 1 日  | 自动计算上月账期，幂等生成             |
| 逾期扫描 | 每日 08:00 | 读 `sys_config` 罚息参数，标记 OVERDUE |
| 逾期通知 | 每日 09:00 | 分组发催缴邮件                         |
| 支付同步 | 每 2 小时  | 对账 30 分钟前待确认订单               |

**为什么这么选**：

- 用 XXL-Job 统一调度，任务可配置、可监控、可重跑；罚息参数放进 `sys_config` 热配置，不改代码即可调费率。

### 3.11 前端 —— 可视化 + 移动端自助

**做什么**：管理后台（Vue3 + Element Plus）与业主端（Vue3 + Vant 移动适配）。

**解决什么问题**：管理人员可视化操作；业主用手机即自助缴费/咨询。

**怎么实现**：

- 管理端：路由守卫 + 静默刷新（`refreshing` 标志 + `waiters` 数组实现并发 401 只刷新一次）；
- 业主端：多选账单合计缴费、支付宝跳转、AI 聊天 SSE 流式、移动端适配。

**为什么这么选**：

- 两端完全不同的用户与场景，独立工程、独立部署，权限边界清晰、互不影响。

### 3.12 社区互动 —— 活动 + 论坛 + 投票

**做什么**：管理端发布社区活动、审核帖子与投票；业主端报名活动、发帖评论点赞、参与投票表决。

**解决什么问题**：

- 传统社区通知靠公告单向传达，业主缺乏参与渠道；
- 投票、报名等场景易出现重复操作（一人多投、重复报名）；
- 论坛内容需要管控，违规内容不能直接上墙。

**怎么实现**（[property-module-community](file:///d:/.workspace/javaproject/property-management-system/property-management/property-module-community)）：

- **社区活动**：状态机 `草稿 → 招募中 → 已满员/进行中 → 已结束/已取消`，仅 `招募中` 可报名；活动报名用 `incrSignupCount` 乐观锁定，报名即原子递增、达上限自动转"已满员"，并对同一业主查重；
- **邻里论坛**：发帖经敏感词过滤，命中即自动转"待审核"，人工审核后发布；评论支持两级树形结构（父评论 + 子回复），点赞 toggle 去重；置顶/精华/软删除；
- **投票问卷**：支持单选/多选、匿名/实名；投票状态 `未开始/进行中/已结束`，仅"进行中"可投；同一业主同投票查重，选项计数用 `incrVoteCount` 原子累加，结果按选项聚合投票人。

**为什么这么选**：

- **状态机 + 资格校验内聚到枚举**（`canSignup/canVote/canAudit`）：规则随状态定义走，Controller 只调用不散落判断，新增状态不破坏既有逻辑；
- **报名/投票用原子递增而非锁**：社区场景并发冲突后果轻、频率低，用 `SET count = count + 1` 乐观推进更省资源，与报修审核的行级锁形成对比。

### 3.13 便民服务 —— 报修 + 场地 + 访客

**做什么**：业主在线报修、预约小区场地、为访客生成通行码；管理端审核派单、管理场地与核销通行码。

**解决什么问题**：

- 报修流程线下电话难追踪、责任不清；
- 场地预约多人抢同一时段造成冲突；
- 访客进出靠人工登记，效率低且难核验。

**怎么实现**（[property-module-lifeservice](file:///d:/.workspace/javaproject/property-management-system/property-management/property-module-lifeservice)）：

- **报修工单**：8 态流转 `待审核 → 待派单 → 已派单 → 维修中 → 已完成 → 已评价`，另有"已驳回/已取消"；工单号 `RP+yyyyMMdd+4位流水`；审核/派单/接单/完工用 `selectByIdForUpdate` 行级锁保证状态流转串行；
- **场地预约**：场地类型 1健身房/2棋牌室/3会议室/4游泳池/5其他；预约时段对齐、同一场地同业主月上限、冲突检测（`endTime > start 且 startTime < end` 存在有效预约即拒绝）；开始前 2 小时可取消，超时违约；
- **访客通行码**：6 位 `SecureRandom` 唯一码；核销状态 `有效 → 已用尽/已过期/已撤销`，每次核销递减可用次数。

**为什么这么选**：

- **报修用行级锁**：报修状态流转涉及派单与责任认定，冲突后果重（重复派单/丢单），用 `FOR UPDATE` 串行化最稳妥；
- **场地用时间区间重叠判断而非枚举锁**：时段冲突本质是"区间相交"，用 `gt/lt` 组合判断更精确，无需引入额外锁定机制；
- **通行码用安全随机数**：访客码涉及门禁安全，`SecureRandom` 保证不可预测，唯一性用"生成后查重"兜底。

## 四、贯穿全局的设计决策总结

| 设计决策   | 选择                                   | 为什么                                        |
| ---------- | -------------------------------------- | --------------------------------------------- |
| Token 方案 | JWT 双 Token（短 access + 长 refresh） | 安全与体验平衡，refresh 存 Redis 可吊销       |
| Token 传输 | httpOnly Cookie                        | 防 XSS 窃取，refresh 用 path 限制携带范围     |
| 鉴权粒度   | `@SkipAuth` 注解放行                   | 默认拒绝（fail-closed），放行跟代码走，不易漏 |
| 并发控制   | 按场景分级：金额用悲观锁，车位用乐观锁 | 冲突后果越严重越偏保守，性能与正确性权衡      |
| 支付防重   | 分布式锁 + 行级锁 + 乐观锁 + 幂等四层  | 资金场景"万无一失"，每层补盲区                |
| 回调可靠性 | 被动回调 + 主动对账补偿                | 不依赖单点，保证最终一致                      |
| 计费抽象   | calcType 统一计价公式                  | 新增费用类型只配参数不改代码                  |
| 数据一致性 | 账单幂等生成 + 车位双轨对账            | 自动化任务可重跑，异常主动暴露                |
| AI 集成    | Spring AI + Function Calling + SSE     | 对话接入真实业务数据，回答可信                |
| 社区状态机 | 状态 + 资格校验内聚到枚举              | 规则随状态走，不散落判断，易扩展              |
| 并发分级   | 报名/投票原子递增，报修审核行级锁      | 按冲突后果轻重选并发策略                      |
| 架构分层   | admin/owner 端口与工程隔离             | 权限边界清晰，防越权                          |

## 五、一句话总结

这套系统把物业运营中的 **"计费、收缴、催缴、对账、审计、客服、社区互动、便民服务"** 八件事数字化：**计费用统一的计价模型生成幂等账单，收缴走支付宝在线支付并用多层防重保证资金准确，催缴靠定时任务自动扫描与邮件通知，对账用主动查单与双轨比对兜底，审计用异步日志留痕，客服用 AI 对话打通业务查询，社区互动用状态机与原子递增支撑活动/论坛/投票，便民服务用行级锁与时间区间判断支撑报修/场地/访客**——核心设计主线始终是 **"自动化 + 最终一致 + 按风险分级控制并发"**。
