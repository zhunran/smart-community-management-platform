## 第一梯队 · 高价值核心问题（必问）

### 主题 A：支付防重与并发一致性（本项目含金量最高）

**A-1（浅）**：用你自己的话，从头到尾讲一遍业主发起支付宝缴费、到账单被标记为已缴清的完整链路，包括异步通知和主动对账两条路径。

- 考察点：能否清晰复述核心业务流，而非背术语。
- 参考要点：下单（防重复用待支付订单）→ 返回支付表单 → 回调验签（RSA2）→ 仅处理 TRADE_SUCCESS/TRADE_FINISHED → 三重锁防护 → 更新支付单与账单状态 → 分摊明细。

**A-2（中）**：为什么同一条支付回调要叠三层防护（Redis 分布式锁 + 行级锁 `FOR UPDATE` + 乐观锁）？每一层各自解决什么问题？只留一层会出什么问题？

- 考察点：对"分布式唯一性 + 并发一致性"的分层理解，能否分清各层边界。
- 参考要点：分布式锁解决**多实例**并发；行级锁解决**同库事务**内的串行化读改写；乐观锁兜底**跨服务/重复投递**的最终一致。单层均有盲区。

**A-3（深）**：你的 Redis 分布式锁底层用 `SET NX EX`，为什么不是先 `SETNX` 再 `EXPIRE`？释放锁时为什么必须用 Lua 脚本？

- 考察点：Redis 原子性、锁的"加锁+过期"必须原子，否则加锁后进程崩溃导致死锁。
- 参考要点：`SET key value NX EX ttl` 一句原子完成。Lua 保证"比较 value 是否自己持有 + DEL"两步原子，避免误删他人锁（A 超时后 B 拿锁，A 回来删了 B 的锁）。

**A-4（深）**：你实现的这个分布式锁有什么隐患？假设业务处理时长为 40s，而锁 TTL 只有 30s，会发生什么？如何处理？

- 考察点：锁超时/续期问题（看门狗），这是自研锁 vs Redisson 的关键差距。
- 参考要点：锁提前过期 → 第二个请求拿到锁 → 并发重复处理 → 靠行级锁/乐观锁兜底。方案：Redisson 的 WatchDog 自动续期、锁粒度细化、前置幂等判断。

**A-5（深）**：悲观锁（`FOR UPDATE`）和乐观锁（`@Version` / `WHERE status=?`）本质区别是什么？各适用什么场景？本项目为什么两者叠加使用？

- 考察点：锁的本质（冲突率高用悲观、冲突率低用乐观）、`FOR UPDATE` 依赖事务、乐观锁靠影响行数判断。
- 参考要点：悲观锁阻塞等待、适合写冲突高；乐观锁无阻塞、失败重试、适合读多写少。回调场景低并发，重试成本低，故乐观锁为主，行级锁兜事务内一致。

**A-6（场景）**：如果支付宝回调因为网络抖动一直没到，或者已经到了但你的服务刚好重启导致本地处理丢失，怎么办？你的对账补偿机制如何兜底？

- 考察点：最终一致性与补偿设计的理解。
- 参考要点：主动对账扫描 `status IN (0,1)` 超 30 分钟订单 → 调 `queryTradeSafe` → 按查询结果区分（成功/待支付/超时/失败）。

**A-7（场景·高压）**：同一个 `paymentNo` 同时涌入 100 个并发回调，你的代码最终结果保证正确吗？请画出关键时序，并指出最坏情况下会发生什么。

- 考察点：是否真正理解多层防护叠加后的正确性，以及锁竞争下的性能。
- 参考要点：99 个在 Redis 锁处排队/失败，1 个进入；进入者再被行级锁串行；乐观锁保证只有第一次 status 跳转成功，其余 affectedRows=0 直接返回成功（幂等）。

### 主题 B：JWT 双 Token 鉴权

**B-1（浅）**：为什么采用"Access Token + Refresh Token"双 Token 设计？只用一个长有效期的 Token 会有什么问题？

- 考察点：理解"短效降低泄露风险、长效减少重复登录"的权衡。
- 参考要点：Access 短效 + 含完整用户信息，泄露窗口短；Refresh 长效仅含 userId，用于无感续签。

**B-2（中）**：Access 和 Refresh 的 claims 里分别放了什么？为什么 Refresh 只放 userId？`type` 字段的作用是什么？

- 考察点：最小权限原则，防止 Refresh Token 被当 Access Token 用于业务。
- 参考要点：`type=access/refresh` 区分；`getLoginUser()` 强制校验 `type=access`，Refresh 不能访问业务接口。

**B-3（深）**：Refresh Token 为什么要存 Redis？刷新时做了什么校验？这样设计如何实现"服务端主动吊销某个用户的登录态"？

- 考察点：无状态 JWT 的"有状态化"补丁，服务端可控失效。
- 参考要点：刷新时校验签名 + `type=refresh` + 与 Redis 存储值一致；删除 Redis key 即可立即吊销 Refresh。

**B-4（深）**：Token 通过 httpOnly Cookie 传输，为什么能防 XSS？它同时引入了什么新风险（CSRF），本项目如何缓解？

- 考察点：安全模型理解，能看出"防了这头又要防那头"。
- 参考要点：httpOnly 使 JS 读不到 Token 防 XSS 窃取；但 Cookie 自动携带带来 CSRF 风险，需靠 SameSite、CSRF Token 或从 Header 读取 token 等缓解。

**B-5（深）**：Access Token 黑名单如何实现？key 与 TTL 怎么设计？黑名单放在 Redis 意味着**每次鉴权都要查 Redis**，你如何权衡这个性能代价？

- 考察点：能否意识到"鉴权链路引入依赖"的代价与优化方向。
- 参考要点：`token:blacklist:{token}`，TTL=剩余有效期；查 Redis 的额外 RTT，可用本地缓存 + 短过期缓解，但会弱化即时失效。

**B-6（场景）**：假设一名业主的 Access Token 被盗，攻击者能干什么？你的设计能把损失窗口控制到多小？如何进一步优化？

- 考察点：攻击面分析 + 系统思维。
- 参考要点：Access 短效（如 30min）+ 黑名单 + 业务接口按 ownerId 过滤 → 攻击者最多在有效期内操作该业主数据；可加 IP/设备指纹、滑动过期。

### 主题 C：缓存与一致性

**C-1（浅）**：你的 `SysConfigService` 里 `@Cacheable` 内部调用为什么会失效？你是用 `@Lazy` 自注入解决的，讲一下背后 AOP 的原理。

- 考察点：Spring AOP 动态代理 + 自调用绕代理问题。
- 参考要点：`this.method()` 内部调用不经代理对象，切面不生效；`@Lazy` 注入自身代理，用代理调用即可触发缓存。

**C-2（深）**：缓存穿透、缓存击穿、缓存雪崩分别是什么？本项目有哪些风险点？你会怎么防护？

- 考察点：三种缓存异常场景的区分与对应方案。
- 参考要点：穿透（布隆过滤/缓存空值）、击穿（互斥锁/热点不过期）、雪崩（TTL 加随机/多级缓存/限流）。本项目系统配置查询可为空值加缓存。

**C-3（深）**：缓存与数据库如何保证一致性？是"先删缓存再更新 DB"，还是"先更新 DB 再删缓存"？本项目 sys_config 配置更新后，如何让缓存失效？

- 考察点：Cache Aside 模式及顺序选择。
- 参考要点：通常推荐"更新 DB 后删缓存"，失败可重试 + 延迟双删；本项目应提供 `@CacheEvict` 删除对应 key。

### 主题 D：数据库与性能

**D-1（中）**：`SELECT ... FOR UPDATE` 的底层原理是什么？在 InnoDB 的 RR 隔离级别下，它锁的是"记录"还是"间隙"，什么情况下会升级为表锁？

- 考察点：锁机制、隔离级别、索引对锁范围的影响。
- 参考要点：命中唯一索引锁行、非唯一/无索引锁 Gap 甚至全表（Next-Key Lock），注意可能引发死锁。

**D-2（中）**：你的 `selectByIdForUpdate` 是如何防止"并发超收"的？什么是死锁？在支付/缴费场景，什么操作顺序容易造成死锁？

- 考察点：事务内的锁顺序与死锁规避。
- 参考要点：加锁读账单行 → 计算 → 更新，串行化；多订单回调若加锁顺序不一致（如按不同明细分摊）可能死锁，应统一加锁顺序。

**D-3（深）**：如果 `t_bill` 表到达千万级，你的分页查询（`PageQuery` + MyBatis-Plus）会遇到什么问题？深分页（`offset=100000`）为什么慢？有哪些优化手段？

- 考察点：深分页性能问题与优化方案。
- 参考要点：大 offset 导致回表扫描大量无效行；可用覆盖索引、延迟关联、游标（`WHERE id > lastId`）或换用 ES。

### 主题 E：异步日志落库

**E-1（中）**：操作日志为什么异步落库？为什么用**单线程**守护线程池，而不是普通的多线程线程池？

- 考察点：性能隔离 + 日志顺序性 + 单线程足够。
- 参考要点：不阻塞业务；单线程保证写入顺序（审计日志的时序性）、避免多线程竞争与额外复杂度。

**E-2（深）**：异步线程里为什么拿不到 `RequestContextHolder` 和 ThreadLocal 里的登录用户？你是在主线程"采集上下文快照"解决的，讲一下这个设计的要点和坑。

- 考察点：ThreadLocal 作用域 + 跨线程传参（InheritableThreadLocal / 显式传参）。
- 参考要点：线程池线程与请求线程不同，ThreadLocal 隔离；快照在请求线程采集后传入异步任务，注意引用类型深拷贝与内存泄漏。

**E-3（场景）**：当操作量暴增，单线程日志线程池堆积严重时，会出现什么现象？你会怎么权衡"日志不丢"与"系统不被拖垮"？

- 考察点：队列背压、降级策略。
- 参考要点：有界队列 + 拒绝策略（丢弃/主线程兜底/采样降级），明确业务对审计日志的容忍度。

## 第三梯队 · 架构与设计取舍

**S-1**：管理端（admin-api）和业主端（owner-api）为什么要独立部署、用不同的 JWT 密钥？合并成一个服务有什么问题？

- 参考要点：权限域隔离、降级独立、防止横向越权；密钥分离防止一端泄露影响另一端。

**S-2**：业主端如何实现"只能看自己的数据"的权限隔离？如果未来要加"楼栋管理员只能看本楼栋"，你会在哪一层做？

**S-3**：项目记忆里提到"用 Redis 分布式锁替代 MySQL 的 GET_LOCK"，为什么？GET_LOCK 有什么短板？

- 参考要点：GET_LOCK 绑定单连接、锁无过期需主动释放、依赖数据库连接、难以跨 DB 集群扩展；Redis 更轻量。

**S-4**：为什么用 MapStruct 做字段级权限（管理端可改全字段、业主端只能改部分字段）？不用 MapStruct 的话你会怎么做？

**S-5**：模块之间单向依赖（business → framework → common），你如何判断一个类该放 common 还是 framework？如果 A 模块和 B 模块要互相调用，会踩什么坑？

## 第四梯队 · 数据量增大场景专项（多情况考量）

**P-3（审计日志表）**：审计日志只增不减，一年几千万条，审计统计的 "Top10 模块/用户" 聚合查询会多慢？你会引入什么方案（汇总表/ES/时序库/归档冷热分离）？

**P-4（Redis 内存与热点）**：黑名单 key、Refresh Token、系统配置缓存，随着用户量增长 Redis 内存怎么控制？热点系统配置被高并发读穿透缓存时怎么办？

**P-6（并发缴费）**：缴费日（如月初）大量业主同时缴费，整单缴纳的 `FOR UPDATE` 会形成锁竞争热点，如何削峰？
