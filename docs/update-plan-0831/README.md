# 智慧社区改造更新计划（2026-08-31）

> 目标：在现有物业管理系统基础上，新增**社区互动（community）**与**便民服务（lifeservice）**两个业务模块，把业主端从"缴费工具"升级为"社区入口"。

---

## 一、背景与目标

### 现状

| 维度           | 现状                        | 问题                       |
| -------------- | --------------------------- | -------------------------- |
| 业主端定位     | 查账单、缴费、车位、AI 咨询 | 低频使用，业主一个月来一次 |
| 物业与业主关系 | 单向管理（收费、发通知）    | 缺少互动，无邻里连接       |
| 服务能力       | 无报修、无预约、无访客管理  | 物业服务靠电话/线下        |

### 目标

1. **提升打开频率**：社区活动、论坛、投票让业主每日使用
2. **物业数字化转型**：报修工单、场地预约、访客通行码替代电话登记
3. **架构零侵入**：只新增模块 + 在入口模块加依赖，不改任何现有模块代码

## 六、风险与注意事项

| 风险              | 影响                 | 应对                                                                                                 |
| ----------------- | -------------------- | ---------------------------------------------------------------------------------------------------- |
| 论坛内容合规      | 违规内容引发法律风险 | 先发后审 + 敏感词自动过滤 + 举报入口 + 管理端删除能力                                                |
| 报名/预约并发冲突 | 超员、双抢           | 报名乐观锁 `@Version` + 唯一索引 `(activity_id, owner_id, status)` 兜底；预约 `uk_slot` 唯一索引兜底 |
| 工单状态分支多    | 漏流转、死单         | 状态机集中定义 + XXL-Job 超时扫描兜底                                                                |
| 图片上传          | 磁盘占满             | 第一期本地存储 + 大小/格式校验，接口抽象为 StorageService 便于后期换 OSS                             |
| 新模块拖慢启动    | 无                   | 遵循现有 scanBasePackages + @MapperScan 集中配置模式                                                 |

## 七、不做的事（明确排除）

- 不改任何现有模块的代码（bill/owner/payment/parking/notification/ai/statistic）
- 不引入新中间件（MQ、ES、OSS 均不引入，第三期再评估）
- 不做 App 原生推送（复用邮件通知，第三期评估极光/个推）
- 不做智能硬件对接（门禁、车牌、人脸）
